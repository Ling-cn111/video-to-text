# ASR 基准测试集（asr_benchmark）

对 3 个中文 B站视频（科普 / 讲解(强BGM) / 教程）的前 150 秒音频做 ASR 转写，与参考稿对比 CER。
评测结果与结论见 [docs/asr-benchmark.md](../../docs/asr-benchmark.md)；运行命令见该文「复现」章节。

## 结构

```
asr_benchmark/
├── cases.json         # 评测用例（videoId / 分类 / 链接 / 参考稿路径）
├── refs/<videoId>.txt # 参考稿（首行 # 开头为来源注释，解析时跳过；正文严禁包含时间戳）
├── proofread/         # 任务 C 人工校对底稿（带时间戳，校对完成后用于修订 refs/）
└── results*.csv       # 评测输出（默认写入此处，.audio-bench/ 为本地临时产物不入库）
```

## ⚠️ 新增评测 case 的强制检查项（2026-10-06 审计教训，逐项通过才能跑 CER）

> 背景：讲解 case 的参考稿曾缺失开场 0-60 秒（约 40% 内容），导致该列所有 CER 不可解读、
> 且连带污染了「本地全崩」「Demucs 无效」两个下游结论（详见 docs/asr-benchmark.md「基准缺陷审计与修复」）。
> **参考稿来自单一模型时，尺子自带该模型的时间盲区与家族偏好——新增 case 必须先验 ref 再跑数。**

1. **时间覆盖验证（强制）**——参考稿必须覆盖整个对齐音频段：
   - 用参考稿的生成模型对同一段音频复跑（与 ref 生成同管线），确认**首段 start ≈ 0s、末段 end ≈ 音频末尾**，中间无大段无输出；强 BGM / 唱歌 / 喊叫音频对 faster-whisper 尤其危险（VAD 或模型本身可能整段跳过）
   - **语速 sanity**：归一化后字数 ÷ 音频秒数应在 **3-6 字/秒**（清晰口播类；喊叫/歌唱段落多的可偏低，需人工确认原因）。讲解案例：ref 3.07 字/秒 vs 云端 5.3+ 字/秒 → 暴露漏听
   - **交叉验证**：与至少一个**非同族**引擎（如云端 ASR）转写对比，ref 字符数应达对方输出的 ~80%+（讲解案例：ref 461 vs 云端 795/821 → 暴露缺陷）；difflib 覆盖率过低同样说明 ref 有缺口
2. **参考稿来源与状态写进文件头注释**：生成模型 / 是否人工校对 / 校对范围与日期 / 已知残余问题。人工校对状态分三级：全自动（large-v3）→ 部分人工 → 全文人工（绝对 CER）
3. **正文严禁时间戳**：CER 归一化会把 `0:02` 当作字符计入污染结果；时间戳只出现在 proofread/ 底稿
4. **背景人声重点核对**：喊叫 / 对话插话 / 歌唱段是自动转写最易整段漏掉的（科普案例：ref 缺 8 句背景人声）；生成底稿时这类段落必须显式标注（⚠️ref）
5. **CER 解读纪律**：同一参考稿下的模型横向对比有效；**绝对 CER 必须人工校对参考稿后才成立**；修复参考稿后须重跑全部受影响行并更新 docs/asr-benchmark.md

## 校对流程（任务 C）

1. 用 `backend/.audio-bench/gen_drafts.py`（本地，不入库）从云端转写生成 `proofread/` 底稿
2. 人工听音频修订底稿（⚠️ref / ⚠️q3 标注句优先）
3. 修订后的文本（去时间戳）写回 `refs/<videoId>.txt`，文件头更新校对状态
4. 重跑 benchmark，更新 docs/asr-benchmark.md
